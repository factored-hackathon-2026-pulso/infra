# 0009 The shared Core is agent-core's own `agentcore serve`

Status: **Proposed**. Nothing is applied; merging this creates no resource (ADR 0002 item 7). It decides which Core the
platform and the improvement engine share, on top of [ADR 0007](0007-hackathon-single-host-profile.md) and the agent services
of [docs/agent-services.md](../agent-services.md) (`agent_services_enabled`).

## Context

The core host runs two things that both call themselves Core: `core-runtime` (the engine's composed `core-bridge` image on :8000)
and, with `agent_services_enabled`, agent-core's own `agentcore serve` on :8001 with the tool-service. The owner decided that the
**shared Core is agent-core's own `serve`**: the support platform and the improvement engine talk to the same Core through its
public contract (runs, registry API, export API). The Dockerfile and the build belong to agent-core ([ADR 0003](0003-agent-core-workload.md)).
`core-runtime` is not removed here and is not the shared Core.

## Decision

1. **Mechanism.** The agent-core `serve` deployment is the one in docs/agent-services.md (image `images.core.agent` built from
   agent-core's Dockerfile, real pieces, artifact directories, `FILES__<SVC>__<NAME>` key files). This ADR adds only what the
   engine and the credentials need; it does not duplicate that mechanism.
2. **Credentials generated by Terraform** (like `origin_verify`, written once into the single secret, never rotated by an apply),
   under main's key names: one gateway bearer per consumer (`GATEWAY__GATEWAY_TOKEN_<C>`, including the new consumer `AGENT_SERVE`);
   `CORE__AGENTCORE_LLM_GATEWAY_TOKEN`, `AGENT__AGENTCORE_LLM_GATEWAY_TOKEN` and `PULSO__PULSO_LLM_GATEWAY_KEY` (the name the engine
   reads) equal their consumer's token; with the flag also the grant-check bearer (`AGENT__AGENTCORE_GRANTS_TOKEN` =
   `SUPPORT__CC_INTERNAL_SERVICE_TOKEN`), the tool-service bearer (`AGENT__AGENTCORE_TOOL_SERVICE_TOKEN` and `TOOLS__TOOL_SERVICE_TOKENS`),
   agent-core's HMAC key material, and four Ed25519 keys (`tls_private_key`): the platform's principal, delegation and staff keys and the
   engine's. They become `FILES__AGENT__IDENTITY_KEYS` (platform principal + delegation + engine), `FILES__AGENT__STAFF_KEYS` (platform
   staff + engine) and `FILES__SUPPORT__AGENT_PRIVATE_KEYS`; the engine seed is `PULSO__PULSO_SERVICE_SEED_HEX` (64 hex characters) with
   `PULSO_SERVICE_KID` in SSM. `GATEWAY_CONSUMERS` and `LLM_ENDPOINTS` (alias `openrouter` only) are derived. Model ids need no gateway
   configuration (they ride in each request profile). The sensitive output `generated_secrets` feeds `aws-prod.ps1 seed-secret-keys`,
   the merge-only reseed of an existing secret (adds missing or `CHANGE_ME` keys, keeps every other value, prints key names only).
3. **Engine wiring.** SSM values `PULSO_CORE_ADDR` (core host private IP, port 8001 with the flag, else 8000) and `PULSO_LLM_GATEWAY_ADDR`
   (private IP, 8080): the engine client rejects DNS names. Security groups: core 8080 from the engine (gateway, already published by the
   core compose) and, with the flag, core 8001 from the engine, plus matching egress.

## Trust implication (read before applying)

agent-core checks the roles claimed inside a credential, not a per-key ceiling. Any key listed in the staff-keys document can sign a
credential that claims any role, including `aprobador` with `actor=human` and a `step_up` level: the engine's seed can therefore mint
human credentials and approve, publish or promote. "The engine never approves" is a rule of the engine's code, not a control enforced by
the Core or by infrastructure. Any key in the identity-keys document can likewise claim any principal. Listing the engine's key is a trust
grant to everything that holds that seed.

Worse, ADR 0007's single secret is readable by all three host roles (the key prefix selects what a host renders, it is not an access
boundary): the engine host and the core host can read the platform's staff seed and every other key. Terraform state holds all seeds in clear.

No offline change removes the grant. Options for the owner: (a) accept the risk for the hackathon with an explicit sign-off (recorded in the
pull request); (b) split the secret per host (one secret and ARN per workload, each host role reading only its own); (c) ask agent-core for a
per-kid role ceiling in `--staff-keys`, after which the engine key can be limited to `constructor` and `exporter`. Until one is done this ADR
records (a) as the accepted risk.

## What is not solved

- **Existing secret.** The secret version ignores later changes: use `aws-prod.ps1 seed-secret-keys` (merge only). Never `terraform apply -replace`
  the secret version: it resets every out-of-band key (DB passwords, TOTP key, session secret) to `CHANGE_ME`.
- **Out of band** (agent-services.md): DSNs (eval DSN different from the registry DSN), migrate DSNs, `AGENT__AGENTCORE_JEV_API_KEY`, field grants and
  overlay files, bank links, provider keys, DB passwords, trained calibration and classifier artifacts. The platform is a gateway consumer but has no gateway path here.
- **Engine contract, as the engine code reads it today** (improvement-engine `seams/crates`): `PULSO_LLM_GATEWAY=enabled`, `PULSO_LLM_GATEWAY_ADDR`, `PULSO_CORE_ADDR`
  (IP literals), `PULSO_LLM_GATEWAY_KEY`, `PULSO_SERVICE_KID`, `PULSO_SERVICE_SEED_HEX`. Residual mismatches for the engine team: the live Core port
  (`PULSO_CORE_PORT=live`, `real_core.rs`) is built for the old core-bridge (`PULSO_BRIDGE_ADDR`, `PULSO_HUMAN_KID`/`PULSO_HUMAN_SEED_HEX`, `PULSO_LIVE_*`) and is not
  provided here; the engine has one model per process (`PULSO_LLM_GATEWAY_MODEL`), not one per role; infra provides no human seed, by design.

## Consequences

Apply on a stack built from main adds the tls/random resources, two SSM values for the engine and the gateway rule, and changes the two
gateway SSM values in place (`moved` blocks, no destroy). `user_data` is untouched: no instance is replaced.
