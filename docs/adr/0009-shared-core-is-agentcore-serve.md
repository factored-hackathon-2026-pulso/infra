# 0009 The shared Core is agent-core's own `agentcore serve`

Status: **Proposed**. Nothing is applied; merging this creates no resource (ADR 0002 item 7). It corrects the core host of
[ADR 0007](0007-hackathon-single-host-profile.md) and applies [ADR 0003](0003-agent-core-workload.md): the Dockerfile and the
build belong to agent-core.

## Context

The hackathon core host ran the improvement engine's composed runtime (`core-bridge`, `command: runtime`, a core-exporter and
the bridge signers). The owner decided that the shared Core is the agent-core repository's own image, `agentcore serve`,
because the support platform and the improvement engine must talk to the same Core through its public contract: runs API,
registry API (`--registry-api`) and export API. Gaps G1, G5, G9, I1, I2, I3 of
`docs/reports-claude/SHARED_ATTACH_GAPS_2026-10-04.md` (workspace report) are closed here.

## Decision

1. **Image.** `core-runtime` is built from agent-core's own `Dockerfile` at a pinned commit (`aws-prod.ps1 images -Service
   agent-core -AgentCoreDir <checkout> [-AgentCoreCommit <40 hex>]`). The zip is the agent-core checkout alone; the commit
   (verified clean and equal to the checkout when it is a git repository) is the `GIT_SHA` build argument. The ECR repository
   and the image key keep their names (`pulso-prod/core-runtime`, `images.core.core`) so bootstrap and deploy tooling do not
   change. Deployed by digest only.
2. **Core host.** `core-migrate` (`agentcore migrate`), `core-runtime` (`agentcore serve --registry-api` with `--identity-keys`
   and `--staff-keys` files, real tools/authz/field-classifier/grant-active adapters) and `llm-gateway`. `core-exporter` is
   removed: the Core's own `/v1/export/*` and `/registry-events` replace it. The gateway port 8080 is now published on the
   core host.
3. **Wiring.** Env `AGENTCORE_*`: DSNs (out of band), `AGENTCORE_LLM_GATEWAY_URL` (compose name) and token (generated),
   `AGENTCORE_TOOL_SERVICE_URL`/`_TOKEN` (out of band, both or neither; no tool service is deployed yet),
   `AGENTCORE_GRANTS_URL`/`_TOKEN` (the platform's grant check), keys fingerprint and token map (generated),
   `AGENTCORE_FIELD_CLASSIFICATION_FILES` (the overlay `deploy/hackathon/core/field-overlay.json`, copied from agent-core's
   e2e overlay), `AGENTCORE_AUTHZ_BIND_KEYS`, `AGENTCORE_SERVE_AGENTS`. The platform host gets `CC_AGENT_CORE_URL` and
   `CC_AGENT_KEYS_FILE`; the engine host gets the gateway address, the Core address and its credentials.
4. **Credentials generated by Terraform** (like `origin_verify`, written once into the single secret, never rotated by an apply):
   one gateway bearer per consumer (`GATEWAY__GATEWAY_TOKEN_<C>`, mirrored as `CORE__AGENTCORE_LLM_GATEWAY_TOKEN` and, for the
   engine, `PULSO__PULSO_LLM_GATEWAY_KEY`, the name the engine reads); the grant-check bearer (`CORE__AGENTCORE_GRANTS_TOKEN` =
   `SUPPORT__CC_INTERNAL_SERVICE_TOKEN`); four Ed25519 keys (`tls_private_key`): the platform's principal, delegation and staff keys
   and the engine's. Public halves are assembled into the Core's identity-keys document (platform principal + delegation + engine)
   and staff-keys document (platform staff + engine); the platform's private seeds become `SUPPORT__AGENT_KEYS_JSON`; the engine's
   seed is `PULSO__PULSO_SERVICE_SEED_HEX` (64 hex characters) with kid `PULSO_SERVICE_KID` in SSM. The key documents are plain
   secret values rendered into the service env files; the compose entrypoints write them to `/tmp` inside the containers before the
   service starts (the platform entrypoint starts people-only, with a log line, when its document is not seeded). There is no host
   file mechanism: the start script (part of `user_data`) is deliberately untouched so no instance is replaced. Model ids need no
   gateway configuration (they ride in each request profile): `GATEWAY_CONSUMERS` and `LLM_ENDPOINTS` (the `openrouter` alias only)
   are derived. A sensitive output `generated_secrets` feeds `aws-prod.ps1 seed-secret-keys`, the merge-only reseed of an existing
   secret (adds missing or `CHANGE_ME` keys, keeps every other value, prints key names only).
5. **Network.** Core SG: 8080 from the engine SG (gateway). Platform SG: 8081 from the core SG (a second Caddy listener that
   exposes only `/api/v1/internal/grants/*`, because the Core cannot send `X-Origin-Verify`). Matching egress rules. Names are
   the private DNS records `core.<zone>` and `platform.<zone>`; the Core's 8000 was already open to the engine and the platform.

## Trust implication (read before applying)

agent-core checks the roles claimed inside a credential, not a per-key ceiling. Any key listed in the staff-keys document can sign
a credential that claims any role, including `aprobador` with `actor=human` and a `step_up` level: the engine's seed can therefore
mint human credentials and approve, publish or promote. "The engine never approves" is a rule of the engine's code, not a control
enforced by the Core or by infrastructure. Any key in the identity-keys document can likewise claim any principal. Listing the engine's
key is a trust grant to everything that holds that seed.

Worse, ADR 0007's single secret is readable by all three host roles (the key prefix selects what a host renders, it is not an access
boundary): the engine host and the core host can read the platform's staff seed and every other key. Terraform state holds all seeds in clear.

No offline change removes the grant. Options for the owner: (a) accept the risk for the hackathon with an explicit sign-off
(recorded in the pull request); (b) split the secret per host (one secret and ARN per workload, each host role reading only its
own) so the engine host cannot read the platform staff seed: a change to `hackathon_data`, `hackathon_iam` and `hackathon_compute`
that replaces the secret and was not made here; (c) ask agent-core for a per-kid role ceiling in `--staff-keys`, after which the
engine key can be limited to `constructor` and `exporter`. Until one of these is done this ADR records (a) as the accepted risk.

## What is not solved (and who must act)

- **Pieces.** agent-core main (46d7b98 and newer) ships the real transcript store (`agent_core.composition.transcript:transcript`),
  calibration source and classifier provider (`agent_core.composition.artifacts:calibration` and `:classifier_provider`); the compose
  uses them by default (`agent_core_serve_pieces` overrides). Calibration and classifier read trained artifacts from directories
  (`AGENTCORE_CALIBRATION_DIR`, `AGENTCORE_CLASSIFIER_ARTIFACTS_DIR`), mounted from `deploy/hackathon/core/calibration/` and
  `classifier/` of the S3 bundle. They ship empty (a `.keep`); the data team's trained artifacts are still open in agent-core.
- No tool service is deployed: `AGENTCORE_TOOL_SERVICE_URL` (SSM) and `AGENTCORE_TOOL_SERVICE_TOKEN` (secret) are human-owned `CHANGE_ME` placeholders that `http_tool_executor` rejects, so the Core does not start until the owner sets both (fail closed),
  there is no `AGENTCORE_AUTHZ_FIELD_GRANTS_FILE` (without it no field can be read through a tool) and the data-governance
  field-classification catalogue is not shipped (fields no file classifies stay `pii_direct`).
- `AGENTCORE_JEV_API_KEY` and the provider keys are out-of-band secrets. `AGENTCORE_EVAL_DSN` must be a different database from
  `AGENTCORE_REGISTRY_DSN` (the Core refuses equal DSNs); both are set by the owner (docs/db-bootstrap.md). Migrations run with the same DSN as the runtime.
- The secret version ignores later changes (precedent: `origin_verify`). On an existing secret use `aws-prod.ps1 seed-secret-keys` (merge
  only). Never `terraform apply -replace` the secret version: it resets every out-of-band key (DB passwords, TOTP key, session secret) to `CHANGE_ME`.
- **Engine contract, as the engine code reads it today** (improvement-engine `seams/crates`): `PULSO_LLM_GATEWAY=enabled`, `PULSO_LLM_GATEWAY_ADDR`
  and `PULSO_CORE_ADDR` as IP literals of the core host (SSM, from `aws_instance.private_ip`; the engine rejects DNS names), `PULSO_LLM_GATEWAY_KEY`,
  `PULSO_SERVICE_KID`, `PULSO_SERVICE_SEED_HEX`. Residual mismatches for the engine team: the live Core port (`PULSO_CORE_PORT=live`, `real_core.rs`) is
  built for the old core-bridge (`PULSO_BRIDGE_ADDR`, `PULSO_HUMAN_KID`/`PULSO_HUMAN_SEED_HEX`, `PULSO_LIVE_*`) and is not provided here; the engine has
  one model per process (`PULSO_LLM_GATEWAY_MODEL`), not one per role; infra provides no human seed, by design.
- The platform is also a gateway consumer; no gateway path is opened for it here.

## Consequences

The `core-bridge` runtime and its bridge-signer secrets are no longer deployed by the hackathon stack (the `bridge_services` module
for `staging`/`prod` is untouched). `terraform apply` on a stack built from the previous main would add resources and change a few
in place; it destroys nothing (see the pull request for the exact list).
